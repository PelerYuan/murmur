# Murmur 后续待办（v1 之后）

排序原则：P1 = v1 发布后立刻值得做，缺了它日常使用会明显痛；P2 = 明显增值，等 P1 稳定后做；P3 = 有想法但需要先验证需求。

"v1 预留"一列说明**v1 的数据模型或契约现在就要留口子**，否则后面要做破坏性迁移。标记为"必须"的条目，建议在 M1–M4 实现时一并处理；标记为"建议"的是成本很低、值得顺手做；"无需"表示后续纯增量即可。

## P1

### 1. 推送提醒渠道（ntfy / Bark / Telegram / Webhook）｜P1｜v1 预留：必须（轻）

v1 的提醒只在网页开着时才生效，而"到点叫我"恰恰常发生在人不在屏幕前时。这是 v1 最大的功能缺口，用户已明确要求。做法是把提醒投递抽象成"渠道"：每个渠道实现一个 `send(todo)`，Core 在 `remind_at` 到点时对所有启用的渠道投递，网页 SSE 只是其中一个渠道。ntfy 与 Bark 只是一个 HTTP 请求，先做；Telegram 需要 bot token 与 chat id 的配置引导；Webhook 提供 JSON 模板，兼容 Home Assistant 等。**v1 预留**：不要把"提醒已送达"等同于"网页端点了确认"——`reminder_state` 的状态机（`pending/fired/acked`）保持渠道无关；设置分组名 `notify` 预留；`fired` 的含义是"已投递到至少一个渠道"。每个渠道需要自己的失败重试与投递日志（后续新表即可）。

### 2. 隐私控制：定时暂停、勿录时段、快捷暂停｜P1｜v1 预留：必须

这是被"一直在听"的产品最重要的信任基础，尤其是工作室同事与来访客人场景。v1 只有录音端的手动 `enabled` 开关。后续提供：①"暂停 30 分钟 / 1 小时 / 到明天"一键按钮，带自动恢复；②每周计划的勿录时段（如 22:00–07:00、周日全天）；③有客人时的"访客模式"（只录音量，不转写）；④录音中的明确可见指示（录音端 LED/网页顶栏）。**v1 预留**：录音端 `config_json` 必须是可扩展的 JSON（API 已是），暂停到期时间应由 Core 下发的配置计算（`enabled=false` + `resume_at`），而不是由录音端本地计时，这样网页和手机都能看到并取消；心跳响应里的 `server_time` 已可用于对时。建议 v1 的网页暂停按钮就按这个语义做。

### 3. 备份与恢复、数据导出｜P1｜v1 预留：建议

自托管用户最怕的是一次磁盘故障带走几个月的转写和声纹。M5 已列"备份"，这里细化：①一键导出完整备份（SQLite 一致性快照 + `speaker_samples` + 加密设置，打成一个归档）并支持从归档恢复；②按日期范围导出转写为 Markdown/JSON/SRT，按说话人、房间筛选；③设置页提示备份新鲜度（"上次备份：7 天前"）。声纹是生物特征数据，导出与备份文件需要加密选项，并在界面里提醒。**v1 预留**：所有状态都在数据目录与单个数据库里，不要散落在其他位置；密钥文件（`MURMUR_SECRET_KEY`）与数据分开说明；`MURMUR_STORAGE` 抽象保证备份能覆盖 S3 形态；文档先写手动备份步骤。

### 4. 说话人合并建议与撤销合并｜P1｜v1 预留：必须

说话人是签名功能，而聚类天然会把一个人分成多份，用户需要"系统告诉我哪些可能是同一个人"。后续：①`GET /speakers/suggestions` 用质心余弦相似度找出疑似同一人的对（介于 `match_threshold` 与 `cluster_threshold` 附近），说话人页顶部出现"可能是同一人"卡片并排试听；②合并撤销（一段时间内可撤）；③定期"重新聚类"建议（声纹漂移时）。**v1 预留**：合并目前不可逆，是整个说话人体验里最让人不安的一环。最低成本的预留是软合并：`speakers` 增加可空的 `merged_into_id`，并在 `utterances` 保留单句声纹的 `utterance_embedding_days` 窗口内记录合并日志（被合并话语 id 列表），这样撤销只需要反向移动话语和重算质心。若 v1 来不及做撤销，至少保证这两个字段与日志在 M2 写入，避免日后无法补建历史。

### 5. 按人 / 按房间的每日摘要｜P1｜v1 预留：必须

PLAN 第 9 节已列"按房间/按人的摘要视图"。对共享空间尤其有用：工作室同事只想看"与我有关的今天"，家人想看"孩子今天说了什么"（涉及隐私，需要和账号体系一起设计权限，见第 16 项）。做法：生成摘要时可选 `speaker_id` 范围，只把该说话人的话语（及其前后上下文）送给 LLM，输出"他/她今天提到的事、做出的承诺、待办"。待办页的"只看我的"与此配套。**v1 预留**：`summaries` 已有可空 `room_id`，需要同样加上可空 `speaker_id`；同时 `summaries` 增加可空 `meta_json`（用于存说话人引用，见下条，也供第 12 项记录统计）。`POST /summaries/generate` 的请求体允许未知字段时预留 `speaker_id`。

### 6. MCP server 与 Skill｜P1｜v1 预留：建议

用户已明确要求：让外部 agent（Claude Code、桌面助手）能问"我这周和谁约了什么""昨天的日报""搜一下提到装修的话"。MCP server 暴露只读工具：`search_utterances`、`get_summary`、`list_todos`、`list_speakers`、`get_day`；Skill 提供使用建议与提示词模板。核心难点是认证与隐私：必须使用**独立的只读 API 令牌**（可范围限制：按房间/按时间/是否含声纹），而不是复用网页会话，且每次调用写入审计日志。**v1 预留**：REST API 保持版本化稳定（`/api/v1`）；认证中间件抽象成"请求主体（principal）"（网页会话、录音端 token 都是主体的一种），之后加 API 令牌不用改路由；令牌表后续新增即可，不影响现有表。

## P2

### 7. 说话人感知搜索（全文 + 语义）｜P2｜v1 预留：无需

v1 已有 FTS5 子串搜索和 `speaker_id` 筛选。后续做成独立搜索页：按"谁说的 + 什么时候 + 在哪间房 + 关键词"组合，保存常用搜索，结果按对话段分组而不是逐句；再加语义搜索（对话段文本向量，支持"那次聊过的装修预算"这种模糊记忆）。语义搜索需要新增文本向量表与离线回填任务，是纯增量，不影响 v1 表结构。中文 trigram 对 1–2 字词无效的限制，在此一并解决（例如对短词走 LIKE 回退）。

### 8. 唤醒词"记一下"与语音笔记｜P2｜v1 预留：必须（轻）

用户在家里最自然的操作是对空气说"记一下：周六去买灯泡"，而不是等 LLM 从闲聊里猜。检测基于转写文本（"Murmur，记一下 …"或"note this …"），命中后直接创建高置信度待办或笔记，并在时间线上高亮。不需要单独的唤醒词引擎——ASR 已经转写，规则匹配即可，且能容忍中英混杂；缺点是依赖转写延迟（几十秒），不能做即时反馈。**v1 预留**：`todos.source` 目前是 `auto|manual`，枚举需允许扩展 `voice`；后续新增 `notes`（自由笔记）表即可。待办抽取流程不要写死"只能来自 LLM"，设计成可由多个来源写入。

### 9. 大屏"今天"面板｜P2｜v1 预留：无需

用户已列。`/today` 全屏页：时间、今日摘要要点、未完成待办（按截止时间）、录音在线状态、提醒整屏高亮，适合挂在客厅平板或墙屏上。需要**只读展示令牌**（URL 里带令牌，或单独的展示会话），避免大屏长期持有管理会话。内容复用概览页的卡片组件（PRODUCT.md 第 2.8 节）；做成纯前端增量，加上令牌机制后依赖第 6 项的认证抽象。

### 10. 更好的麦克风与回声消除｜P2｜v1 预留：无需

用户已列，也是风险表第一条。摄像头麦克风远场收音弱、AGC 失真。方向：①文档级建议与实测数据（阵列麦克风、会议麦克风，M0 报告的延伸）；②录音端侧可选软件处理：降噪、WebRTC AEC3（需要回采参考信号，常见做法是把电视/音箱的输出作为参考）、波束成形（需要多通道设备）；③多麦克风同房间的去重（两只麦克风录到同一句话）。回声消除只有在能拿到参考信号时才有效，所以这是"硬件 + 录音端"的联合项目，与 Core 无关，不改数据模型。

### 11. 更多语言与 ASR 适配器｜P2｜v1 预留：无需

用户已列。v1 的 ASR 契约（`/v1/process`）和 OpenAI 兼容模式已经隔离了模型。后续：官方适配器与示例（faster-whisper、FunASR、云端 STT 的 diarization 能力对接）；日语、韩语、粤语的语言提示与默认模型建议；声纹模型更换时的**迁移工具**（声纹维度或空间改变后，旧声纹不可比较，需要提示"重新学习"或保留旧模型版本）。**注意**：`speakers.centroid` 应记录所属 `embedding_model`，否则换模型后会静默出错；这一条在 M2 实现时顺手加列（可空），列入建议。

### 12. ASR 质量指标与健康看板｜P2｜v1 预留：建议

没有指标就无法知道换模型/调阈值是否更好。展示：每日话语数、被过滤的话语数与原因（非语音/幻觉/低置信度/忽略说话人）、平均置信度、处理延迟分位数、处理失败率、未命名说话人占比、每个说话人"被手动改归属"的次数（是识别准确度的代理指标）。**v1 预留**：被过滤的话语不入库，所以现在就要在 `chunks` 上留可空 `meta_json`，记录每片的丢弃计数与原因；`utterances` 的"被手动改归属"可由 `PATCH` 时写事件日志。数据一开始就记，后面看板才有历史。

### 13. 日历集成｜P2｜v1 预留：无需

待办里带 `due_at` 的条目很自然地对应日程。第一步只读：提供一个 ICS 订阅地址（带令牌），在手机日历里看到 Murmur 抽出的"明天下午三点开会"；第二步 CalDAV 写入，把确认过的待办推到日历。反向读取日历以改善"明天"的歧义消解和会议摘要（"这次是不是日历上的周会"）属于更远的想法。数据已有 UTC 的 `due_at/remind_at`，无需改表。

### 14. PWA、Web Push 与 HTTPS 部署指引｜P2｜v1 预留：无需

第 1 项的补充：做成可安装的 PWA，并通过 Web Push 在手机上推送提醒，不依赖第三方应用。前提是安全上下文（HTTPS），局域网部署需要反向代理（Caddy/Traefik）和内网证书的文档，这也让浏览器通知 API 在局域网可用（v1 在 http://IP 下无法使用）。先写文档与 compose 示例，再做 Push。

### 15. "问问今天"：基于转写的对话式问答｜P2｜v1 预留：无需

在网页里问"今天谁说过要买牛奶？""这周我们讨论装修说了什么？"，系统检索相关对话段（第 7 项）再让 LLM 回答，并引用出处链接回时间线。这是 MCP 的网页对应物，价值很高但依赖良好的检索与"引用必须可点回原话"的约束，防止 LLM 编造。隐私上必须只使用已配置的 LLM，并在界面里提示"这些原话将发送给你配置的模型"。

### 16. 账号与权限｜P2｜v1 预留：必须

用户已列，也是工作室同事场景最大的限制。v1 单密码意味着任何人能看所有人的对话。后续：多用户、角色（管理员/成员）、可见性规则（谁能看哪个房间、谁能看谁的话语、谁能管理说话人）、说话人与账号关联（"我"就是账号对应的说话人）。这是最重的一项，改动横切所有 API，所以必须在 v1 就留口子：①所有 API 通过统一的 `current_principal` 依赖取得主体，不在路由里直接读单例 `auth`；②`sessions` 增加可空 `user_id`；③`todos`、`speakers` 预留可空 `owner_id`/`visibility`（默认 `shared`），先不使用；④前端的"我是谁"（PRODUCT.md 第 12.6 节）设计成账号上线后可无缝替换。

## P3

### 17. 服务端对话分段与话题标签｜P3｜v1 预留：无需

v1 的对话段由前端按 5 分钟间隔规则切分。后续由服务端分段（间隔 + 说话人变化 + 话题漂移），落成 `conversations` 表，每段有标题与话题标签，摘要与搜索以对话段为单位，也让时间线分段在多端一致。需要先看 v1 的规则切分够不够用，再决定是否值得引入。

### 18. 话语编辑历史与原文保留｜P3｜v1 预留：建议

用户在时间线手改转写后，原始 ASR 文本就丢了，难以评估 ASR 质量（第 12 项）或回滚误改。建议 `utterances` 增加可空 `text_original`（仅在被编辑时写入），并在界面标"已修改"。几乎零成本，趁 `PATCH /utterances` 实现时一起做。完整的版本历史则是 P3。

### 19. 循环待办与日程｜P3｜v1 预留：无需

"每周五提醒我倒垃圾"这类重复事项。需要 RRULE 与提醒再生成逻辑，并处理"自动抽取到重复事项时如何去重"。先观察用户是否真的会口头设定重复事项，再做。

### 20. UI 更多语言与命令面板｜P3｜v1 预留：无需

v1 只有中文与 English。后续引入日文等 UI 语言（文案已按 i18n 键组织即可，社区贡献友好），并加入 `Cmd/Ctrl+K` 命令面板（跳转、搜索、切换主题、暂停录音）。纯前端增量。

### 21. 审计日志｜P3｜v1 预留：无需

记录谁在何时试听了声纹样本、导出了数据、删除了话语、使用了 API 令牌。单租户个人使用时价值有限，但一旦有账号（第 16 项）或 MCP 令牌（第 6 项）就变得重要。新增事件表即可，与前述各项的写入点对接。
